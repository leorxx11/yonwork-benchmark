# YonWork / WorkBuddy 整轮模型调用监控待办

日期：2026-09-22。状态：待实现。前置修复提交：`ecaa372`。

## 目标与边界

一轮 benchmark 从发起到收尾，逐次记录经过受控入口的模型请求，覆盖工具续答、
客户端重试和已验证路由的辅助模型/子代理。两个产品使用同一份记录结构和验收标准。
每轮同时报告“采到了什么”和“哪些部分无法确认”，不以拿到一份汇总用量代表完整采集。

建议路径：`YonWork / WorkBuddy → 请求采集代理 → NewAPI → 上游模型`。
产品日志补充会话、工具和任务状态；代理记录请求；NewAPI 补充上游及计费证据。
代理是待验证方案，先确认两款产品的协议与关联能力，再确定实现。

范围不包含桌面 UI 延迟、答案正确性，以及供应商内部不可见的执行过程。
代理看到的客户端请求与 NewAPI 内部转发尝试分层计数，不能把一次请求默认当作一次上游尝试。
未经过受控入口的调用不能声称已覆盖；辅助模型路由未确认时，整轮覆盖状态必须保留未确认。

## 当前起点

- 已完成测量正确性修复：缺失不填 0、来源独立汇总、耗时口径修正、CLI/Worker 共用锁。
  见 [修复与验收](measurement-correctness.md)。
- WorkBuddy 经 NewAPI 的单次文本调用已通过真实验证，CLI 与后台 token 一致。
  见 [接入验收](workbuddy-newapi-validation.md)；不代表工具续答或子代理全量采集已完成。
- YonWork `runner/newapi.py` 的逐轮采集按请求主模型过滤，需处理一轮内多模型的情况。
- WorkBuddy 目前提供整轮 CLI 用量，解析会保留最后一条 provider usage/model；
  缺少可靠的逐请求账本，NewAPI 仍靠事后时间窗对账。
- 时间窗和串行锁不是精确请求关联；后台消费/错误日志也不能单独证明所有请求均已记录。

## 待办顺序

### 1. 验证入口和任务关联（先做，决定后续方案）

- [ ] 列出两款产品实际使用的协议、端点和路由：主模型、辅助模型、子代理。
  分别验证可否经过采集入口，记录产品版本；不能根据主模型配置推定其他路由相同。
- [ ] 验证每轮唯一标识的可行方式：透传标记、独立 endpoint 或令牌映射。
  产品不支持时明确限制；令牌只用于映射，不把凭据写进日志或版本库。
- [ ] 用连续两轮和隔离的外部请求验证归属，确保不串单；不能精确归属的记录单独保留。
  保留现有串行锁，本项不以解除并发限制为目标。
- [ ] 确定任务收尾规则：产品终止、在途请求、迟到请求和后台子任务分别处理。
  安静一段时间只能作为等待策略，不能单独证明任务不会再发请求。

交付：入口与关联验证记录，列出已验证路线、未覆盖路线以及选定方案。

### 2. 建立逐请求账本和采集代理

- [ ] 定义 run / request / upstream attempt 的关联结构。每次客户端请求分配稳定 ID；
  parent、重试关系、上游 ID 只有证据支持时填写，不能按相邻时间猜测。
- [ ] 记录产品、任务标识、请求模型、响应声明模型、协议、开始/首个有效输出/结束时间、
  HTTP 状态、终止原因、错误/取消、usage 及来源。响应模型名不等于已证明真实部署模型。
- [ ] 请求开始即落盘，流式响应边收边转发，保留断流、超时、客户端取消和解析错误。
  缺 usage、缺结束事件均保留缺失状态；代理不自动重试，不改变产品请求次数。
- [ ] 明确普通文本与工具参数输出的首个有效输出定义，不把响应头或空事件算成首字。
  记录代理测量边界，并评估额外开销，不把观测耗时称为纯模型计算时间。
- [ ] 默认只记录所需元数据；不记录鉴权头、完整提示词或工具结果。诊断原文另设显式开关、
  脱敏和保存期限，遵循现有本地产物不入 Git 的规则。
- [ ] 支持 JSONL 重放入库与幂等导入，保留稳定 ID；旧数据标记为无逐请求记录，不能伪造历史链路。
- [ ] 接入 Docker 一键环境，补配置模板、健康检查与回退步骤；兼容 Windows/WSL 宿主机驱动。

### 3. 接上两个产品及 NewAPI 对账

- [ ] YonWork 按已验证关联收集该轮全部模型请求，去掉“主模型过滤即可代表整轮”的假设；
  将工具调用 ID、会话与请求关联，关联不上时保留原始证据和原因。
- [ ] WorkBuddy 保留每次可观察的调用记录，区分 CLI 整轮汇总与逐请求 usage，
  接入逐轮后台采集，不再依赖最后一条 assistant 表示整轮模型和用量。
- [ ] 核实本机 NewAPI 版本的稳定请求 ID、错误记录和内部重试可见性；
  `/api/log/self` 查询内编号不能当成跨查询稳定 ID。
- [ ] 按可靠关联对账，分别展示代理、产品、NewAPI 的证据。缺少 NewAPI 内部重试证据时，
  上游尝试数保持未知；CLI、代理和后台用量不得相加。
- [ ] 分开保存路由覆盖、请求归属、请求终止、usage 覆盖状态及理由。
  无请求、漏采、采集失败与已确认 0 次错误分别处理，由断言层决定判定。

### 4. 报告与验收

- [ ] Web 支持整轮展开逐请求时间线，显示工具/子代理关联证据、失败、取消和未归属请求。
  区分整轮经过时间与请求耗时之和，并发请求不能相加冒充整轮耗时。
- [ ] 按来源汇总调用和 token，显示有效覆盖数；费用只展示已核对的计费数据。
  部分记录的用量只能称为已观测小计，采集不完整时错误数不能显示为确定的 0。
- [ ] 用可控替身测试请求完整性，再做两个产品的实机验收；保留配置版本、运行命令、
  BenchmarkId、脱敏证据和未决项，更新结论文档，不回写历史 verdict。

| 验收场景 | 必须证明 |
|---|---|
| 单次文本问答 | 一轮一请求，归属明确，终止和用量可核对 |
| 工具调用后续答 | 首次请求、工具执行和续答关系有证据，不重复累计 usage |
| 请求失败后重试 | 失败未漏记；区分客户端新请求与网关内部尝试 |
| 多模型 / 子代理 | 各路线逐项验证；不支持或未覆盖明确列出，不计为通过 |
| 超时 / 取消 / 流中断 | 已开始的请求仍在账本中，缺失终止或用量不补零 |
| 连续两轮及外部请求 | 不串单，迟到/无法归属请求不会偷偷并入下一轮 |
| 采集器中断与重放 | 未完成请求可识别，重放不重复计数，故障不伪装为完整数据 |

完成标准：两款产品在已声明路线内通过上述适用场景，报告能回答“这一轮发生了哪些
模型请求、各自结果是什么、哪些信息仍不可见”。没有完成路由及收尾验证前，不宣称整轮无遗漏。
