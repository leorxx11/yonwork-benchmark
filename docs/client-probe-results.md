# 客户端体验探针 · S1–S7 结果（2026-09-21）

判据见 `client-probe-protocol.md`，**那份文件在这些数据产生之前就定稿了**。
原始数据：`results/client-probe/*.jsonl`，21 轮，7 个场景各 3 轮。

## 先说最重要的：这批数据测的不是用户真实链路

**发起方式决定了界面走不走流式**，这是跑完之后做对照实验才发现的：

| 发起方式 | `text-update` | 首段内容出现 | 字符数轨迹 |
|---|---|---|---|
| **UI 发起**（点推荐词 + 点发送） | **18 次** | 用户气泡后 1111ms | 7→51→205→466→959→1275，逐步增长 |
| **API 发起**（`/api/chat/send`） | **1 次** | ≈ 后端答完那一刻 | 一次性灌出 |

下面这张表是关键证据——**首字滞后 ≈ 后端剩余时长**，差值相对量级很小：

| | 首字滞后 | 后端总时长 − 首字 | 差 |
|---|---|---|---|
| S2#1 | 11086 ms | 10822 ms | +264 |
| S3#1 | 46651 ms | 50286 ms | −3635 |
| S4#1 | 8336 ms | 8537 ms | −202 |

也就是说 API 发起时，**界面是在后端「全部答完」那一刻才显示第一个字的**。
`ui_lag_first_ms` 在这条路上量到的根本不是渲染开销，而是「界面在等完成」。

⚠️ **所以 S3 那个「空白 45 秒」不能当成产品缺陷上报。** 真实用户走的是 UI 发起，
那条路是流式的。这正是 CLAUDE.md 三节警告 `openclaw agent --json` 的同一类失真：
**测的不是用户真实链路，做产品基准会失真。**

## 判据结论

| | 判据 | 结果 |
|---|---|---|
| **P1** | 各受控场景首字滞后中位数 < 1000ms | **不适用** —— 指标被发起方式混淆，见上 |
| **P2** | 全场景 Long Task 最大值 < 200ms | **通过**，最差 182ms |
| **P3** | 归一化完成滞后倍率 < 3× | **算不出来** —— 指标定义有缺陷，见下 |

### P2 通过，而且比预期更强

| 场景 | 字数 | Long Task 个数 × 最大值 |
|---|---|---|
| S1 纯文本 | 138 | 0 × 0 ms |
| S2 60 行表格 | 1681 | 1 × 66 ms |
| S3 250 行表格 | 7303 | 1 × **133 ms** |
| S4 表格+代码+列表 | 1087 | 1 × **182 ms** |
| S5/S6/S7 | 129–299 | 0 × 0 ms |

**结论比原本想要的更强**：API 发起时全文是**一次性**灌进 DOM 的，
那是主线程阻塞的**最坏情况**（没有增量摊薄）。即便如此，
渲染 7303 字的表格也只阻塞了 133ms，混合结构最多 182ms，都没到 200ms 的线。

⇒ **renderer 本身不是瓶颈。** 这是个合格产出——协议里写明了「排除客户端瓶颈本身就是合格产出」。

### P3 的定义有缺陷（诚实记录）

我把 P3 定成「`ui_lag_complete_ms / (answer_chars/1000)` 的最大/最小倍率」。
**这个量会变成负数**：UI 最后一次变化经常早于 SSE 流正式终止
（S3 实测 −3.6s），负数之间求倍率没有意义，所以算出来是 `null`。

这是**我预注册时没想清楚**，不是数据的问题。按协议规矩，
改判据要单独提交并说明改之前看过什么数据——所以这里只如实记为「算不出来」，
**不追认一个新指标再声称它通过了**。

想测的东西（客户端开销是否随复杂度超线性放大）仍然值得测，
但得换个不会变号的量，而且要在 UI 发起的路上测。

## 其它站得住的结果

- **历史长度没有影响。** S7（会话里已有 6 轮历史）首字滞后中位数 1276ms，
  S1（2 轮历史）1329ms，在同一水平。`history_turns` 这个协变量在当前量级上不显著。
- **S5 / S6 没测到它们该测的东西。** 两个场景是冲着工具调用和产物面板去的，
  但三轮的 `tool_calls` **全是 0**，模型压根没调工具。
  所以它们只是两个普通短文本场景，**不能当作「工具场景没问题」的证据**。
  要真测，得先搞清楚这个构建里有哪些工具、怎样的 prompt 能稳定触发。

## 跑批过程中撞到的两个工具自身问题（已修）

1. **CDP websocket 被 keepalive 掐断。** S3 渲染 250 行表格时 renderer 主线程卡住，
   DevTools 消息循环跟着停，pong 回不来，`websockets` 默认 20s 超时就主动断连
   （`ConnectionClosedError: keepalive ping timeout`）。改成 `ping_interval=None`。
   **我们测的恰恰是「renderer 忙到什么程度」，保活机制和这个目的直接冲突。**
2. **一轮坏掉拖垮整批。** `except (ProbeError, OSError)` 接不住上面那个异常
   （它不是 `OSError`），整个场景集在第 7 轮就中止了——**正是 PAD 时代第 1 条问题的形状**。
   已改成和 `batch.py` 一样的宽兜底 + 保留 Ctrl-C 出路。
   逐轮落盘救回了前 6 轮，没白烧。

## 结项决定（2026-09-21）

**不继续投入。** renderer 不是瓶颈这个产出已经拿到，剩下的是「不同结构的渲染成本缩放」，
而那需要让 UI 发起一轮受控 prompt——不打字只能三选二（见 CLAUDE.md 第 2 批）：
点推荐词干净但 prompt 固定，点编辑能控 prompt 但**追加不替换**（实测 turnCount 4，
被测轮带着前一轮 1687 字答案跑），只有打字能全占。

**不做的理由是这个数据取不取、结论都一样**：若 CDP 点击与真人差距大，
模拟点击就不代表真实用户，再自动化也只产出不可信数据；若差距小，
剩下要测的缩放效应实测只有 30ms（1693 字表格 1081ms vs 846 字纯文本 1111ms）。
两条路都指向不做，所以**连「CDP 点击 vs 真人」这个对比都不必再测**。

⚠️ UI 驱动白名单保持 1 个动作（`open-session`）。编辑重发那条路作废，
只存在过于一次性验证脚本，没进过仓库。

下面是结项时仍然成立的观察，留作将来重启的起点：

1. 用 UI 发起的路重测 S1–S4。难点是**不打字**地把受控 prompt 送进输入框——
   点推荐词只能拿到固定的几个 prompt，控制不了「恰好 250 行表格」这种。
   直接写 `textarea.value` 对 React 受控组件不可靠，而且已经越过「只点击」的边界了。
2. ~~watch 模式拿不到后端时长~~ **这条已被推翻（2026-09-21 当天实测）。**
   `GET /api/events` 是个**全局 SSE 流**，会推送**任何来源**发起的轮次，
   带 `runId` / `sessionKey` / `state:"delta"` / `deltaText`。
   拿它和我们自己发一轮做对照：首个 `deltaText` 在 **+2.805s**，
   自家 SSE 客户端测的 `first_delta_seconds` 也是 **2.805s**，逐毫秒一致。

   ⇒ **UI 发起的轮次也能拿到后端时长**，差值指标不再依赖「必须由我们发起」。
   所谓「两种模式各有各的固有盲区」是错的，那只是我们没订阅这个端点。

   新形态：CDP 装观察器量 DOM + 订阅 `/api/events` 取后端时长 + UI 发起一轮，
   三者凑齐就能在**用户真实链路**上算出完整的客户端开销。
   时钟规矩不变：`/api/events` 只取**时长**（WSL 时钟内相减），
   绝对时刻仍然一律用 renderer 的 `performance.now()`。
3. 这样一来**打字与否变成了一个小得多的问题**：不打字就能测真实链路的完整差值，
   只是 prompt 只能用应用自带的那几句固定推荐词；
   要测「恰好 250 行表格」这种受控内容的缩放（也就是 P3 想问的），才需要打字。
4. 想清楚上面这些之前，不要再往 S5/S6 上花时间——它们连工具都没触发。
