## 要回答的问题

**Agent 的数据到达客户端之后，YonWork 在呈现不同复杂度的内容时，有没有引入可感知的延迟？**

注意这**不是**「YonWork 快不快」。后端耗时已经由主链路（`runs` 表的 `first_delta_ms` /
`duration_ms`）在测，这里只测**客户端那一段**，做法是把后端时长当被减数减掉。

## 指标定义

全部时间点在 **renderer 内**用 `performance.now()` 打，同一时钟。
Host API 侧只取**时长**（与时钟无关）。实测 Windows 比 WSL 快 7.85s，跨端相减必错。

| 指标 | 定义 | 性质 |
|---|---|---|
| `ui_lag_first_ms` | UI 首次出现回答文字 − 后端首字 | **差值**，后端波动大部分抵消 |
| `ui_lag_complete_ms` | UI 最后一次变化 − 后端完成 | **差值** |
| `long_task_max_ms` | 本轮最长的主线程阻塞片段 | **绝对量，不抵消** |
| `long_task_count` | >50ms 阻塞片段的个数 | **绝对量，不抵消** |
| `text_updates` | DOM 文本变化次数 | 流式分片节奏 |
| `answer_chars` | 实际渲染的字符数 | 归一化分母 |

差值类 3～5 轮就够（后端波动抵消）；**绝对量不抵消**，必须报区间。

## 预注册判据

跑之前定死。**全部满足 ⇒ 判定 renderer 不是瓶颈。**

| 编号 | 判据 | 阈值 |
|---|---|---|
| **P1** | 每个受控场景的 `ui_lag_first_ms` **中位数** | < 1000 ms |
| **P2** | 全部场景 `long_task_max_ms` 的**最大值** | < 200 ms |
| **P3** | 归一化完成滞后 `ui_lag_complete_ms / (answer_chars/1000)`，S1 到最复杂场景之间的倍率 | < 3× |

- **P1 不过** ⇒ 客户端在「让用户看到第一个字」这件事上有可感知开销，指出是哪个场景。
- **P2 不过** ⇒ 渲染把主线程卡住了，这是**纯客户端问题**，后端快慢与它无关。
- **P3 不过** ⇒ 开销随内容复杂度**超线性**放大，说明渲染路径对某种结构特别敏感。

⚠️ **「排除客户端瓶颈」本身就是合格产出**，不要求一定发现问题。

## 报告规则

- **报中位数 + 最小/最大，不报均值。** 本项目实测同一句「你好！」inputTokens
  在 5,514～16,238 之间跳，均值在这种分布上没有意义。
- **样本不足标记**：某场景某指标 `(max − min) > 中位数` ⇒ 标「样本不足」，
  **不用它下结论**，只报原始值。
- 每轮的 `history_turns` 一并记录，它是协变量（DOM 里挂的历史越多渲染越贵）。

## 场景集

**受控场景**（输出长度由确定性指令锁定，参与 P1/P3 比较）：

| | 内容 | 压的是什么 |
|---|---|---|
| S1 | 三句纯文本 | 基线 |
| S2 | 60 行 Markdown 表格 | 表格渲染 |
| S3 | 250 行 Markdown 表格 | 表格渲染 × 4 |
| S4 | 30 行表格 + 40 行代码块 + 20 项嵌套列表 | 混合结构 |
| S7 | 在一个已有长历史的会话里发 S1 | 历史长度对渲染的影响 |

**不受控场景**（输出长度和结构取决于模型当轮行为，**只看 Long Task 和 `text_updates`，
不参与 P1/P3 的归一化比较**）：

| | 内容 | 压的是什么 |
|---|---|---|
| S5 | 多轮工具调用 | Agent 流程，不是 renderer |
| S6 | 工具 + 产物面板 | 产物面板渲染 |

分开看是有理由的：2.3MB 文件那类场景压的是 Agent / 文件处理，
**长 Markdown 才压 renderer**。混在一起比会得出错误结论。

## 已知的待归因现象

跑之前就见过一次，这轮要看它复现不复现：

> 纯文本约 2271 字**流式平滑**（约 45 次更新）；
> Markdown 表格约 2309 字则**先空白 11 秒、然后一次性整块出现**。
> **不是长度差异，是结构差异。**

如果复现，`text_updates` 会明显偏低而 `ui_lag_complete_ms` 明显偏高。
但**这一层分不清是 renderer 缓冲还是上游分片**——探针只看得到 DOM。
要归因得再看 SSE 原始流的分片节奏，那是另一件事，本轮不做，只如实记录。

## 执行方式

每轮**全新会话**，由探针自动建、自动点开（`runner/client_probe/ui.py`）。
`history_turns` 恒为 2（热身那一轮），所以跨轮可比。
S7 例外：它要的就是长历史，用 `auto=False` 往预先养出来的会话发。
